# Домашнее задание 1: «Медиа-Пульс»

## 1. Анализ требований проекта

«Медиа-Пульс» объединяет сбор новостей на Python, хранение и обработку данных в Supabase и веб-интерфейс на Next.js. Проект имеет **повышенную сложность**: необходимо согласовать несколько компонентов и обеспечить надёжный поток данных от RSS-источников до аналитики. По тематике это Big Data-проект, однако реальные требования к масштабированию следует уточнять по объёму новостей, числу источников, частоте сбора и сроку хранения.

Для разработки важен доступ к локальным материалам: исходному коду парсера, коду Next.js, конфигурации, миграциям схемы Supabase и тестовым данным. При работе с локальными базами, резервными копиями или выгрузками агенту следует предоставлять только необходимые обезличенные данные. Подключение к рабочей базе Supabase должно выполняться отдельно и с минимально необходимыми правами.

**Требования безопасности:** API-ключи и другие секреты нельзя отправлять в промпты, передавать облачным LLM или коммитить в Git. Локальные секреты хранятся в `.env`, исключённом через `.gitignore`; для деплоя используются секреты платформы. Ключ Supabase `service_role` разрешено использовать только на серверной стороне, никогда в браузерном коде Next.js. Если правила проекта запрещают передачу исходного кода облачным моделям, необходимо использовать локальную модель или работать без облачного AI-агента.

**Бюджет ограничен.** При выборе инструмента нужно учитывать стоимость подписки и возможную отдельную оплату API-моделей по числу токенов. Предпочтительны бесплатный или образовательный доступ, лимиты расходов и локальные модели, если их качество и производительность достаточны.

## 2. Сравнительный анализ инструментов

Шкала: **1** — наименее благоприятно, **5** — наиболее благоприятно. Для стоимости 5 означает меньшие расходы; для безопасности — меньший риск при корректной настройке. Оценки ориентировочные: доступные функции, тарифы, модели и политики обработки данных могут меняться.

| Инструмент | Доступ к контексту | Скорость | Качество кода | Стоимость | Безопасность | Удобство |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Cloud-агенты | 3 | 3 | 4 | 2 | 1 | 3 |
| GitHub Copilot | 4 | 5 | 4 | 4 | 3 | 5 |
| Cursor | 5 | 4 | 4 | 3 | 2 | 5 |
| Cline | 5 | 3 | 4 | 4 | 4 | 3 |

**Краткое обоснование:**

- **Cloud-агенты** удобны для автономных задач и работы с удалённым репозиторием, но не всегда видят локальные файлы и рабочую базу. Контекст проекта передаётся облачной среде, поэтому при запрете отправки секретов их применение ограничено.
- **GitHub Copilot** хорошо интегрирован в IDE и особенно быстр для повседневных правок. Контекст доступен из workspace, но облачную обработку нужно учитывать: секреты и чувствительные данные следует исключать.
- **Cursor** удобен для навигации и изменений по нескольким файлам, обычно хорошо использует контекст открытого проекта. Это не гарантирует локальную обработку: риск зависит от выбранной модели и настроек.
- **Cline** работает в IDE, поддерживает разные модели и запрашивает разрешение на многие действия. Можно выбрать локальную модель, но при использовании облачного API исходный код передаётся его провайдеру; стоимость зависит от тарифа и объёма запросов.

Для «Медиа-Пульса» практичен IDE-агент с доступом к локальному workspace. `.env`, дампы базы и персональные данные нужно исключить из контекста; при требовании не передавать облачным LLM даже исходный код следует выбрать локальную модель.

## 3. Настройка рабочего окружения

Для разработки выбран IDE-агент **GitHub Copilot**. Рабочее окружение подготовлено в Visual Studio Code: установлены расширения GitHub Copilot и Copilot Chat, выполнен вход в аккаунт. Агент используется непосредственно в редакторе и получает контекст открытых файлов проекта.

Для вызовов облачных моделей из приложения API-ключ провайдера хранится локально в `.env`; файл исключён из Git через `.gitignore`. Ключ не вставляется в промпты, исходный код или логи. Сам Copilot работает через авторизованный аккаунт, поэтому API-ключ в `.env` относится к отдельным интеграциям приложения, а не заменяет авторизацию Copilot.

## 4. Практическое применение

Copilot был протестирован на реальной задаче проекта: с его помощью сгенерирован Python-скрипт для сбора новостей из RSS-лент и сохранения результатов в SQLite. Агент помог определить структуру таблиц для статей и написать SQL-запросы для поиска и фильтрации новостей.

SQLite используется в прототипе для локальной разработки. В целевой архитектуре проекта предусмотрено хранение данных в Supabase; при переходе к нему схему и запросы потребуется адаптировать к выбранной конфигурации PostgreSQL.

## 5. Выводы и рекомендации

GitHub Copilot подходит для разработки «Медиа-Пульса»: он работает рядом с кодом в IDE, помогает учитывать контекст нескольких файлов и ускоряет написание парсера, SQL-запросов и компонентов приложения. Локальная SQLite-база может обрабатываться кодом проекта без отдельной передачи её содержимого в облако.

При этом Copilot — облачный агент: передача контекста зависит от открытых файлов, настроек и используемых функций. Поэтому `.env`, API-ключи, дампы базы и персональные данные необходимо исключать из контекста и никогда не отправлять в чат. Для задач с чувствительными данными рекомендуется сочетать Copilot для общей разработки с локальными моделями, которые позволяют обрабатывать такой контекст без обращения к облачному LLM.
