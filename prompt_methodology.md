# Методология пошаговой разработки промптами

## Выбранная задача

Создать в целевом веб-приложении «Медиа-Пульс» дашборд на Next.js с фильтрацией новостей по периоду, источнику и категории, поиском по заголовку и графиками по времени и категориям. Источник данных — Supabase. Текущий репозиторий содержит локальный прототип на Streamlit и SQLite; приведённые ниже промпты относятся к целевой архитектуре Next.js/Supabase и предполагают, что её файлы и схема доступны агенту.

Вместо запроса на полную внутреннюю цепочку рассуждений задача разбита на этапы с краткими обоснованиями, явными результатами и проверяемыми критериями. Каждый этап можно передавать агенту отдельно, используя результаты предыдущего.

## Шаг 1. Контракт данных и критерии

**Промпт агенту**

```text
Role: Ты — Senior Full-Stack Developer и аналитик данных проекта «Медиа-Пульс».

Task: Подготовь контракт данных и критерии приёмки для дашборда новостей с фильтрами по датам, источнику и категории, поиском по заголовку и графиками.

Context:
- Целевой стек: Next.js, TypeScript strict mode и Supabase/PostgreSQL.
- Изучи существующие миграции, типы и правила доступа; не предполагай наличие столбцов, которых нет в схеме.
- Секреты и реальные данные не выводи и не включай в примеры.

Format:
1. Кратко перечисли факты о существующей схеме и неизвестные вопросы.
2. Предложи тип ответа для списка новостей и агрегатов графиков.
3. Определи параметры фильтров, обработку пустых значений, пагинацию и ожидаемую сортировку.
4. Составь проверяемые критерии приёмки и укажи нужные индексы/миграции, если они действительно необходимы.
Не изменяй код на этом шаге.
```

**Ожидаемый результат:** согласованный контракт данных, перечень неизвестных предположений и критерии, по которым можно проверить UI и запросы. Этот результат становится входом для шага 2.

## Шаг 2. Серверный слой чтения и фильтрации

**Промпт агенту**

```text
Role: Ты — Senior TypeScript/Next.js Developer проекта «Медиа-Пульс».

Task: Реализуй серверный слой чтения новостей и агрегатов дашборда по контракту из шага 1. Поддержи период, источник, категорию, поиск по заголовку, сортировку и пагинацию.

Context:
- Сначала изучи текущую структуру Next.js, клиент Supabase, типы и политики RLS.
- Используй только подтверждённые поля схемы и параметризованные запросы.
- Привилегированные ключи не должны попадать в браузерный bundle; не читай и не выводи .env.
- Сохраняй существующие публичные интерфейсы, если их изменение не нужно для задачи.

Format:
1. Краткий план и файлы, которые планируешь изменить.
2. Реализация с путями файлов и явными TypeScript-типами.
3. Тесты для комбинаций фильтров, пагинации и пустого результата.
4. Команды проверок и их фактические результаты; отдельно перечисли непроверенное.
```

**Ожидаемый результат:** типизированные серверные функции или route handlers, которые применяют фильтры на стороне Supabase, не загружая всю таблицу в браузер, и тесты для их поведения.

## Шаг 3. Интерфейс и графики

**Промпт агенту**

```text
Role: Ты — Senior Frontend Developer, работающий с Next.js и доступностью интерфейсов.

Task: Создай страницу дашборда «Медиа-Пульс», подключив её к серверному слою из шага 2. Добавь фильтры периода, источника и категории, поиск, таблицу новостей и графики по дням и категориям.

Context:
- Используй контракт шага 1 и реальные типы/функции шага 2.
- Следуй дизайн-системе и структуре компонентов, уже принятым в проекте.
- Предусмотри состояния загрузки, ошибки и отсутствия результатов; фильтры должны работать совместно.
- Не выполняй запросы с секретами из клиентских компонентов и не дублируй серверную бизнес-логику в UI.

Format:
1. Краткий план.
2. Изменения по путям файлов с типами компонентов и обработчиков.
3. Тесты взаимодействий фильтров и доступности основных контролов.
4. Кратко укажи ручные сценарии проверки страницы.
```

**Ожидаемый результат:** страница с работающими комбинируемыми фильтрами, таблицей, графиками и явными состояниями загрузки/ошибки/пустого результата. Компоненты используют данные серверного слоя, а не обращаются к Supabase с привилегиями из браузера.

## Шаг 4. Интеграционная проверка и безопасность

**Промпт агенту**

```text
Role: Ты — Senior QA/Full-Stack Engineer, проверяющий готовность функции к слиянию.

Task: Проверь дашборд новостей целиком: фильтры, поиск, пагинацию, агрегаты, обработку ошибок и безопасность доступа.

Context:
- Сверь реализацию с контрактом и критериями приёмки шага 1.
- Проверь серверный слой шага 2 и UI шага 3, а также RLS Supabase.
- Используй тестовую базу или моки. Не обращайся к production-данным и не выводи секреты.

Format:
1. Сначала перечисли найденные дефекты с серьёзностью и путями файлов.
2. Для каждого дефекта укажи воспроизводящий тест или проверку.
3. Исправляй только дефекты в рамках дашборда, добавь регрессионные тесты.
4. Запусти релевантные тесты, линтер и typecheck; сообщи фактические результаты.
5. В конце укажи остаточные риски и критерии, которые требуют ручной проверки.
```

**Ожидаемый результат:** отчёт по дефектам, исправления с регрессионными тестами и результаты проверок. Если дефектов нет, агент должен явно это сказать и перечислить выполненные проверки, а не придумывать изменения.

## Передача результатов между шагами

Перед каждым следующим запросом передавайте агенту контракт и результаты предыдущего шага, а не просите заново угадывать архитектуру. Проверяйте изменения после каждого этапа; не передавайте реальные API-ключи, production-дампы или персональные данные в облачный промпт.
